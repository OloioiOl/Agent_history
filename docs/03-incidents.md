# 실패 사례와 수정

## 1. 중계 모델의 불필요한 개입

- **관찰:** 초기 Hermes 중계가 요청·응답을 바꾸고 토큰 사용을 늘렸다는 사용자 경험.
- **판단:** 더 강한 모델을 사용하는 것만으로 전달 경로의 책임을 해결하지 않기로 했다.
- **변경:** 독립 agy 봇으로 직접 호출 경로를 만들고, 후속 브리지에서는 원문 전달·검증을 코드로 구현했다.
- **미측정:** 전후 토큰 절감률과 데이터 변형 빈도. 다음은 사용자가 회고한 구체적 동작이며 원본 전후 로그는 확보하지 않았다.

| 사용자 관찰 | 구조에서 드러난 문제 | 후속 판단 |
|---|---|---|
| `!pro`를 만나면 정해진 스킬을 바로 찾기보다 “이게 무엇인가”부터 분석하는 경우 | 명령 분기가 자연어 해석에 의존 | 명시적 명령은 코드가 분기하게 한다 |
| Gemini Pro의 응답을 그대로 전달하지 않고 새 사용자 명령처럼 다시 분석 | 외부 모델의 결과와 사용자 지시의 구분이 중계 단계에서 유지되지 않음 | 독립 봇의 직접 반환 경로를 두고, 위임 결과는 구조화된 도구 출력으로 받는다 |
| Gemini 3.1 Pro와 solar-pro4의 컨텍스트 차이 때문에 중계가 자주 깨졌다고 회고 | 큰 분석 결과를 더 작은 중계 컨텍스트에 다시 넣는 구조의 제약 | 원문을 중계 모델이 재작성하지 않게 하고 반환 크기를 명시적으로 제한한다 |

이것은 모델별 일반 성능 순위나 컨텍스트 사양 비교 시험이 아니다. 각 당시 모델의 정확한 한도, 요청 길이, 빈도, 원인별 실패율은 측정하지 않았다. 반환 32 KiB 제한도 Hermes의 전체 컨텍스트 잔여량을 보장하지 않는다.

## 2. OAuth 로그인 성공을 실제 추론 성공으로 오해할 위험

당시 비공식 통합에서 로그인과 모델 선택이 가능해도 실제 호출은 403으로 실패했다. 인증 완료, provider 지원, 실제 모델 실행을 별도로 확인해야 한다는 교훈을 남겼다. 과거 관찰이며 현재 서비스 정책 안내로 사용하지 않는다.

## 3. 출력 한도 초과 뒤 종료 대기 정지

- **증상:** 초기 Linux 실패 조건 시험이 20분 이상 정지.
- **원인:** reader를 멈춘 뒤 unread pipe를 남긴 채 `proc.wait()`만 기다리고, cleanup 자체에 제한 시간이 없었다.
- **수정:** 프로세스 그룹 종료 → reader 회수 → 저장 없이 남은 출력을 drain하고 reap. cleanup에 5초 제한 및 `CLEANUP_TIMEOUT` 추가.
- **확인:** cleanup 회귀, timeout·취소·동시성 관련 시험. 전체 버전별 시험 범위는 검증 문서에 분리했다.

## 4. 프롬프트와 schema의 빈 findings 모순

- **증상:** 근거가 없으면 `findings=[]`를 제출하라는 지시가 `minItems=1` schema에 의해 거절됨.
- **수정:** 제출 schema는 `minItems=0`, 브리지 성공 판정에는 여전히 최소 1개 유효 finding 필요.
- **결과:** 빈 결과는 `NO_VALID_FINDINGS`로 실패한다. 성공 기준을 완화한 것이 아니다.
- **한계:** large 로그에서 schema 오류보다 먼저 `error_message`가 있었다. 157KB 실패 전체의 원인이 이 모순 하나였다고 단정할 수 없다.

## 5. 등록 성공 후 운영에서 드러난 반환 계약 오류

Discord에서 도구를 찾고 호출했지만 다음 오류가 반환됐다.

```json
{"error":"Tool handler returned unsupported result type: dict","error_type":"tool_result_contract","tool":"bulk_analyze","result_type":"dict"}
```

기존 검사는 플러그인 등록과 내부 핸들러 결과를 확인했지만, 운영 실행기의 결과 형식까지 통과시키지 않았다.

수정은 핸들러 최종 경계에서 `json.dumps`로 JSON 문자열을 반환하도록 한 것이다. 브리지 내부의 구조화 객체나 분석 로직은 그대로 유지했다. 이후 설치된 `model_tools.handle_function_call`로 검사하고, Hermes 재시작 뒤 Discord에서 재시험했다.

```json
{"ok":false,"error":"PATH_DENIED"}
```

이 결과는 경로 거절 동작의 정상 반환이다. 정상 문서 분석 성공으로 계산하지 않는다.

## 6. 적용 명령과 복구 명령을 함께 실행한 운영 혼선

적용 후 안내된 복구 명령도 실행돼 활성화 전 설정으로 돌아갔다. 이를 실패한 적용으로 오해하지 않고 출력으로 상태를 확인했다. 원본과 현재 설정, 저장 후보, 설치 코드의 해시를 대조하는 별도 재적용 절차로 복구했다.

개선점은 실행할 명령과 비상 복구 명령을 명확히 분리하고, 다음 상태를 출력으로 확인하는 것이다. 이후 안내에서는 당장 실행할 명령만 제공했다.

## 7. 157KB 실패: 도구 금지 지시 이후에도 관측된 도구 시도

**상황:** stage-r2에 157,547바이트·4,501줄 합성 입력을 전달한 실제 실행. 프롬프트는 제공된 원문만 분석하고 도구를 사용하지 않도록 지시했다. 최종 실행은 실패했고 `structured_output`이 없었다.

아래 순서는 S4 핸드오프가 보존된 stdout을 분석해 기록한 내용이다. 이 공개 저장소에 raw stdout을 첨부한 것은 아니다.

| NDJSON 줄 | 관측 | 해석 한계 |
|---|---|---|
| 4 | `error_message` | 저장 stdout에 오류 내용이 없어 최초 원인 미확정 |
| 6~7 | `finish(findings=[])` 제출, minItems schema 오류 | 프롬프트와 제출 schema의 모순 |
| 9~10 | `view_file` 단계 및 오류 | 해당 단계가 관측됨; 파일 읽기 성공은 입증하지 않음 |
| 12~13 | `run_command` 단계 및 오류 | 명령 실행 성공이나 파일 변경의 증거가 아님 |
| 14 | 최종 ERROR, RunCommand 거부 기록 | 정상 분석 실패 |

**핵심 발견:** 프롬프트의 도구 금지 지시는 실행 전 권한 차단 장치가 아니었다. 오류가 난 뒤에도 외부 도구 단계가 이어질 수 있으므로 최종 결과만 검사하는 것으로는 중간 진행을 제어할 수 없었다.

**수정:** 제출 schema의 빈 배열 모순을 고치고, stream을 읽으며 첫 오류·알려진 도구 metadata·거부·빈 finish·tool ERROR를 관측하면 실패시켰다. 저장 로그 재생에서 기존 최종 거부 감지는 14번째 줄, 도구 감지 후보는 9번째 줄, schema-r3는 첫 오류인 4번째 줄에서 실패했다.

**확인 범위:** 수정 후 fake 회귀와 저장 로그 재생, 별도 16KB 실제 시험을 수행했다. 동일 157KB 입력의 실제 재시험은 하지 않았고 기존 실패 판정을 유지했다.

이 실행 하나로 “입력이 커져서 도구 시도가 발생했다”는 인과관계를 확정하지 않는다. 최초 오류와 schema 모순 등 여러 조건이 얽혀 있다. 악성 문서에 의한 프롬프트 인젝션 성공을 입증한 사례도 아니다. 관측 후 중단이 실제 부작용을 사전에 막거나 얼마나 많은 토큰을 절약했는지도 측정하지 않았다.
