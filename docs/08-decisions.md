# 결정 기록과 회고

이 문서는 개인 운영·복구 기록과 기술 포트폴리오를 함께 위한 문서다. 아래 결정은 대화와 사용자 설명을 바탕으로 정리했으며, 당시 작성한 ADR을 그대로 복원한 문서는 아니다.

## D1. 명시적 명령의 분기를 모델에게 맡기지 않기

**경험:** `!pro`가 들어오면 스킬에 따라 실행하기보다 의미를 분석하는 데서 시작하는 경우가 있었다.

**판단:** 사용자가 이미 명시한 명령의 라우팅은 확률적인 추론이 필요한 일이 아니다. 모델 성능을 높이는 선택과 별개로 코드가 명령을 해석하는 경로를 둔다.

**결과:** 독립 agy 봇과 Hermes의 prefix guard를 사용했다. prefix guard는 중복 응답을 막는 역할이며, 외부 응답의 내용 검증까지 담당하지 않는다.

## D2. 결과 전달을 새로운 지시 해석과 분리하기

**경험:** Gemini Pro가 돌려준 응답을 Hermes가 사용자에게 넘기는 대신, 새 사용자 명령처럼 다시 분석하는 경우가 있었다.

**판단:** 사용자 지시와 위임 결과는 다른 출처·역할을 가진 데이터다. 결과를 대화 안에 다시 넣는 것만으로 올바른 취급을 기대하지 않는다.

**결과:** 독립 봇에서는 중계 LLM을 빼고, 후속 브리지에서는 결과 schema와 도구 반환 계약을 코드로 다뤘다. Hermes가 최종 답변을 재서술하는 위험은 남아 있어 정상 문서 시험에서 비교할 예정이다.

## D3. 더 큰 모델의 컨텍스트를 중계 모델이 그대로 수용한다고 가정하지 않기

**경험:** 두 모델의 컨텍스트 차이 때문에 요청·응답 중계가 깨졌다는 사용자 회고.

**판단:** 분석 모델이 처리할 수 있는 양과 중계 모델이 다시 받아 설명할 수 있는 양은 다르다. 정확한 모델별 사양은 이 기록에서 확인하지 않았다.

**결과:** 원문은 코드가 읽어 분석 모델에 전달하고 반환 크기는 제한한다. 크기 초과를 잘라 성공으로 처리하지 않는다. 토큰 절감률 및 장문 성공률은 미측정이다.

## D4. 기존 환경을 초기화하고 기본 기능부터 다시 쌓기

**경험:** 스킬·프롬프트·중계 동작이 얽힌 환경을 계속 덧대는 대신 역할을 다시 정하고 싶었다.

**판단:** 백업과 복구 가능성을 남긴 뒤 새 기본 환경을 구성하고, Claude/Discord 기본 동작부터 확인한다.

**결과:** 독립 봇과 후속 브리지를 구분해 구축했다. 초기화가 유일한 해결책이었다거나 기존 데이터가 모두 불필요했다는 주장은 하지 않는다.

## D5. 검사를 통과한 계층만 완료라고 말하기

**경험:** 플러그인 등록 검사를 통과했지만 실제 Discord 호출은 dict 반환 계약 오류로 실패했다.

**판단:** 내부 함수, 설치본 dispatcher, 장기 실행 gateway, 실제 Discord는 서로 다른 검증 대상이다.

**결과:** 설치본 실행기 검사를 추가하고 Discord 재시험까지 수행했다. 정상 문서 분석과 경로 거절 시험도 분리한다.

## 포트폴리오에서 설명할 핵심

내가 어떤 모델을 붙였는지만 나열하지 않고, 명령과 데이터의 책임을 어디에 두었는지 설명한다. 사용자 경험으로 시작한 가설, 코드로 바꾼 부분, 실제 시험으로 확인한 범위, 아직 남은 문제를 함께 보여준다. 구현에는 AI 도구의 도움이 있었고 실제 환경 판단과 서버·Discord 검증에는 사용자가 참여했다.

## D6. 프롬프트의 도구 금지와 실행 통제를 구분하기

**경험:** 157KB 실패 로그에서 도구 금지 지시가 있었음에도 오류 뒤 `view_file`과 `run_command` 단계가 관측됐다.

**판단:** 지시 문구를 권한 차단으로 취급하지 않는다. 결과를 다 받은 후 거부를 확인하는 것과 실행 중 이벤트를 보고 중단하는 것도 다르다.

**결과:** systemd 경로·쓰기 제한과 stream 이벤트 감지를 함께 사용했다. 현재 감지는 관측 이후 중단이며 도구 실행 전 차단이나 완전 격리로 설명하지 않는다. 입력 크기와 도구 시도의 인과관계도 확정하지 않았다. [사건 기록](03-incidents.md#incident-large-input) 참조.
