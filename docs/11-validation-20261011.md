# 2026-10-11: 정상 문서 경로와 Linux 전체 fake 시험

사용자가 서버 명령과 Discord 요청을 실행하고 출력을 제공했다. AI는 진단·수정 후보를 만들고 제공된 결과를 검토했다. 프로젝트 문서 1건의 제한된 검증이며 일반적인 분석 품질이나 보안 전체를 승인하는 기록이 아니다.

## 입력과 두 번의 시도

입력은 당시 검증 현황 문서를 고정한 UTF-8 5,807바이트다. [입력 고정본](../evidence/normal-document-source-20261011.txt)의 SHA-256은 `4a1d18958b0f6ad9008374b7abe5522f470037d5f75e4ba893a53dec7fb611a3`이다. 원문의 미검증 표시는 10월 8일 기록으로 해석했다. 질문은 16KB/157KB 결과, Discord 경로 거절과 systemd 상태, Windows/외부 Linux 시험, 토큰 합계의 의미를 인용과 함께 설명하도록 했다.

| 구분 | 첫 시도 | 두 번째 시도 |
|---|---|---|
| 결과 | AGY_TOOL_ERROR 실패 | 정상 구조화 결과 및 정확한 인용 검증 통과 |
| finding별 근거 수 | 3, 5, 3, 2 | 3, 3, 3, 1, 2, 2 |
| 개별 인용 | 13개 일치, 제출 전체는 실패 | 14개 일치, 제출 전체 통과 |
| 보고 input/output/total | 15,054 / 19,287 / 34,341 | 15,169 / 29,427 / 44,596 |

두 실행의 입력·질문·모델 별칭 `flash`는 동일하다. 첫 실행에서 `finish`의 두 번째 finding에 근거 5개가 들어가 `maxItems: got 5, want 3`으로 거절됐다. 브리지는 도구 ERROR 이벤트에서 중단했다. 개별 인용이 맞더라도 실패를 성공으로 바꾸거나 근거를 잘라내지 않았다.

기존 스키마는 finding당 근거 최대 3개를 이미 규정했다. 프롬프트에도 근거 1~3개, finding 최대 8개, claim·quote 길이와 제출 전 확인을 명시했다. 호스트 브리지 core만 교체하고 브리지 서비스를 재시작했으며, 스키마·검증 코드·클라이언트 플러그인은 유지했다. 자동 재시도 없이 사용자가 두 번째 시험을 시작했다. 한 번의 성공으로 문구 변경의 일반적인 효과나 향후 준수를 보장하지 않는다.

보고 토큰은 비용·쿼터·Hermes까지 포함한 전체 사용량이 아니다. 성공 실행의 step와 final에 같은 44,596이 나타났으므로 한 번만 기록했다. thinking_tokens를 total_tokens에 추가하지 않는다. 기존 308,039는 과거 별도 실행 집계로 유지한다.

## 결과 전달과 내용 보존

- 저장된 입력·질문 및 schema가 예상 값과 일치했다.
- 정상 종료 코드 0, 출력 수집 완료, 정리 오류 없음으로 확인됐다.
- 최종 `result.structured_output` 재검증 결과와 저장된 응답이 일치했다.
- Hermes 세션 DB의 해당 도구 반환을 JSON으로 파싱한 값이 저장 응답과 같았다.
- 후속 assistant 저장 답변의 14개 evidence가 순서·파일명·줄 범위·문자열을 유지했다. Markdown 목록의 표시용 들여쓰기만 제거해 비교했다.
- Discord 전달은 사용자가 제공한 3개 분할 메시지로 확인했다. Discord API 원시 메시지의 바이트 비교는 하지 않았다.

해당 결과 ID의 도구 메시지 하나를 찾은 것은 전체 세션의 CLI 호출 수나 내부 모델 단계 수를 계수했다는 뜻이 아니다. [축약 증거](../evidence/normal-document-20261011.json)에 범위를 남겼다.

## 의미 검토의 한계와 발견

AI가 원문·브리지 주장·최종 답변을 검토한 범위에서 네 주제의 주요 사실과 과거/현재·성공/실패·미검증 구분에 중대한 모순을 발견하지 못했다. 독립적인 사람의 품질 승인은 아니다.

finding 6은 개별 실행의 토큰 수 17,921 / 266,291 / 23,827도 설명했지만, 선택된 인용은 표 머리글과 합계 설명이었다. 숫자는 원문 22~24줄에서 확인되나 선택된 evidence만으로 그 세부 주장 전체를 뒷받침하지 못한다. 최종 Hermes 설명은 개별 숫자를 생략했다. **인용 문자열 일치와 주장에 대한 의미적 뒷받침은 다른 검사**라는 한계가 실제 사례에서도 드러났다.

## Linux 전체 fake 시험

Linux aarch64·Python 3.12.3의 임시 소스 복사본에서 31개를 실행해 모두 통과했다. 실패·오류·skip은 0이며 unittest 시간은 3.862초, 준비를 포함한 측정은 3.913초다. 실행 소스의 바이트는 시험 전후 같았다.

네트워크를 격리하고 운영 브리지 경로 접근을 막은 임시 systemd 서비스에서 일반 사용자로 실행했다. fake 프로세스·임시 Unix 소켓으로 취소·timeout·하위 프로세스 정리·동시성·경로/peer 거절·출력 한도·반환 계약을 검사했다. 실제 모델 호출과 운영 파일 변경은 0이다.

[구조화 결과](../evidence/linux-fake-20261011.json)와 [전체 unittest 출력 발췌](../evidence/linux-fake-20261011.txt)를 제공한다. 시험 소스는 [현재 manifest](../evidence/manifest.json)와 일치한다. 이전 Windows 19통과/12skip 및 외부 Python 3.10의 30/31 보고를 덮어쓰거나 합산하지 않는다.

## 남은 작업

대표 강의 문서의 주장·근거 연결과 품질을 사람이 검토할 기준을 마련한다. 157KB 실패 재시험, 인젝션 자료 확보·통제 시험, 재부팅 복구·반복 안정성은 별도 범위로 남긴다. 완료한 이번 문서 호출과 fake 시험을 단순 반복하지 않는다. 후속 순서는 [다음 검증](05-next-validation.md)에 정리했다.
